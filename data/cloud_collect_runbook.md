## 1. 失敗メカニズムの特定

2026/8/6 に「11店中5店で別店舗の内容が返った」件の原因を再現・特定した。
**別店舗が返る条件は2つあり、どちらも回避可能。**

### 条件A：検索インデックスに無いURLを自分で組み立てると別店舗が返る

| 叩いたURL | 返ってきた店 | 判定 |
|---|---|---|
| `hole_view?hid=343084…(楽園南越谷)&_cb=20260816` ← 自作パラメータ | **マルハン小岩スロット館** | ✕ 別店舗 |
| `hole_view?hid=340001…(SAP草加)&k=3のつく日` ← 自作 | **やすだ八潮店** | ✕ 別店舗 |
| `hole_view?hid=340003…(ピーアーク草加)&k=3のつく日` ← 自作 | **やすだ八潮店** | ✕ 別店舗 |
| `hole_view?hid=270222…(エクスアリーナ)&k=2のつく日` ← 自作 | **やすだ八潮店** | ✕ 別店舗 |
| `hole_view?hid=125006…(マルハン亀有)&k=1のつく日` ← 自作 | **やすだ八潮店** | ✕ 別店舗 |
| `hole_view?hid=270222…(エクスアリーナ)&k=4のつく日` ← 自作 | **パラッツォ馬橋中根長津店** | ✕ 別店舗 |

自作URLは「直前に取得したページ」を返す傾向がある。**URLを自分で組むのは禁止。**

### 条件B：WebSearch の結果に出てきたURLをそのまま叩けば店舗は必ず正しい

検索結果由来のURLは **11/11 すべて店舗名が正しかった**（0件の取り違え）。

### 結論：安全なレシピ

1. まず `WebSearch`（`allowed_domains:["hall-navi.com"]`）で店名を検索する
2. 検索結果に出た **URL文字列をそのまま** `WebFetch` に渡す（改変しない）
3. **1件ずつ直列**で叩く（並列は避ける）
4. 返答の店舗名が検索結果タイトルの店名と一致するか照合 → 不一致なら破棄
5. 「当日」の日付が今日かを照合 → 不一致なら破棄

## 2. もうひとつの罠：店舗は正しいが日付が古い（スナップショット鮮度）

店舗名が正しくても、返ってくるのが数日〜2ヶ月前のスナップショットであることがある。
鮮度は **URLごとに違う**。同じ店でも URL 違いで鮮度が変わる。

| 店 | 素のURL | 検索由来の別URL |
|---|---|---|
| キコーナ松戸 | 6/15（2ヶ月前） | `&k=5のつく日` → **8/16 最新** |
| やすだ三郷 | 8/6 | `&k=9のつく日` → **8/16 最新** |
| 楽園南越谷 | 別店舗が返る | `&k=8のつく日` → **8/16 最新** |
| SAP草加 | 8/3 | `&k=9のつく日` → **8/16 最新** |
| エクスアリーナ松戸 | 8/10 | `&k=毎週 金曜日` → **8/16 最新** |

→ **素のURLで古かったら、検索で別URLを探して叩き直す**と当たることが多い。

**当日日付のアサーションは必須。**これが無いと1ヶ月前の評価を今日の評価として使ってしまう。

## 5. クラウドでは取れないもの

- **X（旧Twitter）の店舗アカウント告知**：ログイン済みセッションが要るため、
  Mac の Chrome拡張が繋がっている時しか取れない。代替コネクタは
  MCPレジストリを検索したが存在しなかった（2026-08-16 確認）。
- **hall-navi の過去レポ差分バックフィル**：素のURLが古いスナップショットを返すため、
  「いつ時点の在庫か」が保証できない。Mac 経由での確認が要る。

## 6. 定期実行の構造的欠陥（修正済み）

これまでの朝/夜ジョブは `send_later`（1回きり）を毎回セッション内で
「翌日ぶんを再設定」する自己連鎖方式だった。
→ **8/10 のセッションで再設定が途切れ、以降ずっと止まっていた**（8/10〜8/16 の6日間）。

対策：`cron_expression` による本物の定期実行に置き換えた。
セッション側が何をしようが鎖は切れない。
